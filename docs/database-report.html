1. Overview§s1§

1.1 Purpose of the system§s1-1§

The Hospital Management System (HMS) runs the day-to-day work of a hospital:

  • registering patients and booking appointments;
  • the outpatient visit, from arrival through triage to the doctor;
  • clinical notes, vital signs, lab orders and results, prescriptions and dispensing, and the bedside medication record;
  • admissions, beds and wards, the emergency queue and ambulances;
  • billing, staff accounts with role-based access, and an audit trail of who did what.

It is a Node.js/Express API over MySQL, with a React client. This report describes the database: the live schema of hospital_db (the development database), read through information_schema and SHOW CREATE, together with the migration files in database/migrations. The older files database/schema.sql and lab_pharmacy_workflow.sql do not match the live database and were not used.

Consistency keys (composite foreign keys)

Nine tables are kept outside BCNF on purpose (section 6.4): a row stores a patient, doctor or medicine that it could also reach through a nullable link. Each such link has a composite foreign key to a UNIQUE key on the parent covering the id and the copied columns, so the database refuses a copy that disagrees with its link. InnoDB checks a composite foreign key only when none of its columns is NULL, so rows without the link are unaffected. All are ON DELETE RESTRICT; the single-column foreign key on the same link keeps its own ON DELETE rule.

6. Normalization§s6§

6.1 Method§s6-1§

Each table is judged strictly:

  • 1NF: atomic values, no repeating groups.
  • 2NF: no non-key attribute depends on part of a candidate key.
  • 3NF: no non-key attribute depends on another non-key attribute (no transitive dependency).
  • BCNF: every determinant is a candidate key.

Verdicts:

  • Y holds;
  • N does not hold, and the explanation names the dependency;

Tables whose only key is a single surrogate column satisfy 2NF automatically for that key; 2NF matters here only for their composite candidate keys.

6.3 Decompositions made§s6-3§

Each decomposition followed the same steps, one commit each:

  1. Back up hospital_db, then rehearse the migration on a copy of the live data.
  2. An additive migration checks the dependency on every row and stops with an error if a row breaks it. It makes the redundant column nullable (or computes it by default) so that nothing has to write it, and keeps old reads working (a view or join).
  3. The code reads the value from its one owner. API requests and responses are unchanged: same fields, same order.
  4. Run the server suite, browser suite, stress test and patient-journey test, then compare the schema of hospital_db with the test database (schema-diff: no differences).
  5. After every item passed, migration 022 re-checked each rule and dropped the redundant columns.

  • Parent keys.   • Rows without a link. A composite foreign key is checked only when all its columns are non-NULL, so an order with no visit, or a stock movement from before batches, is accepted as before.
  • Errors. 6.6 Deliberate denormalization: stored totals and mirrors§s6-6§

Besides the copies of section 6.4, the schema stores four kinds of value that could be derived from other tables. None of them breaks BCNF inside its table (each is an aggregate or a mirror of another table), but each is redundancy: it makes an important read cheap or keeps a historical value. Each has a named anomaly risk and a named mechanism that prevents it.

  • Dispensing marks the items dispensed, and the after_prescription_dispense trigger takes the same quantity off stock_quantity; the service takes it off the batches in the same transaction.

Anomalies at this stage:

  • Update: changing the phone means editing four rows.
  • Insertion: a test cannot be recorded without a medicine.
  • Deletion: removing the last medicine loses the diagnosis.

1NF → 2NF (remove dependencies on part of the key):

  • patient facts depend only on the patient;
  • visit facts depend only on (patient, visit time);
  • dose, frequency and quantity depend on (visit, medicine);
  • the result depends on (visit, test);
  • cost depends on the test alone.

So the relation splits into PATIENT(patient, dob, gender, phone), VISIT(visit, patient, doctor, dept, dept_floor, time, symptoms, diagnosis), VISIT_MEDICINE(visit, medicine, dose, freq, qty), VISIT_TEST(visit, test, result) and TEST(test, cost). A surrogate key is added for each entity (patient_id, encounter_id, …), because names are not unique.

2NF → 3NF (remove transitive dependencies):

  • In VISIT, dept and dept_floor depend on the doctor, not on the visit (visit → doctor → department → floor). That gives DOCTOR(doctor_id, name, department_id) and DEPARTMENT(department_id, name, floor).
  • A visit's note is written by the doctor, so symptoms and diagnosis move to a note (consultation) of the visit. One visit can then have several notes.
  • Medicines become a catalogue, MEDICINE(medicine_id, name, …), and what a doctor prescribes is grouped under a prescription header.

BCNF. Every remaining determinant is a key:

  • (prescription, medicine) lines get their own id;
  • a lab result is determined by its order;
  • a test's cost by the test.

8. Triggers§s8§

There are seven triggers. All are row-level (FOR EACH ROW) and run inside the statement that fires them, so they are part of the same transaction: if the trigger fails, the statement fails and rolls back.

8.1 after_admission_discharge§s8-1§

Timing, eventAFTER UPDATE ON admissions
What it doesOnly on ACTIVE → DISCHARGED: frees the bed (AVAILABLE), subtracts 1 from the doctor's workload, and closes the open bed_assignment_log row with the discharge time.
Why a triggerThe reverse of the insert trigger, for the same reason. It fires only on that exact transition, so re-saving a discharged admission changes nothing.
Without itBeds would never become free and workloads would only grow, so the allocator would run out of beds and doctors. Known gap: an admission inserted already DISCHARGED fires the insert trigger but never this one, leaving the bed OCCUPIED. The seed data did exactly that, and migrations 004 and 005 repaired it.
BEGIN
    IF OLD.status = 'ACTIVE' AND NEW.status = 'DISCHARGED' THEN
        UPDATE beds SET status = 'AVAILABLE' WHERE bed_id = OLD.bed_id;
        UPDATE doctors SET current_workload = current_workload - 1 WHERE doctor_id = OLD.doctor_id;
        
        UPDATE bed_assignment_log 
        SET released_at = NEW.discharge_date, status = 'RELEASED'
        WHERE admission_id = NEW.admission_id AND status = 'ACTIVE';
    END IF;
END

8.2 after_admission_insert§s8-2§

Timing, eventAFTER INSERT ON admissions
What it doesMarks the bed OCCUPIED, adds 1 to the admitting doctor's current_workload if the admission is ACTIVE (since migration 020; an admission inserted already discharged does not count), and opens a bed_assignment_log row (ACTIVE) for the admission.
Why a triggerWhoever creates an admission (the API, sp_admit_patient, sp_allocate_emergency, or an administrator at the SQL prompt), the bed, the workload and the history change in the same statement. No caller can forget a step.
Without itWithout it, an admitted bed would stay AVAILABLE and could be given to a second patient. Workload would stop limiting a doctor's admissions, and the bed history would have gaps.
BEGIN
    UPDATE beds SET status = 'OCCUPIED' WHERE bed_id = NEW.bed_id;
    -- Workload is the number of ACTIVE admissions; one inserted already discharged does not count.
    IF NEW.status = 'ACTIVE' THEN
        UPDATE doctors SET current_workload = current_workload + 1 WHERE doctor_id = NEW.doctor_id;
    END IF;

    INSERT INTO bed_assignment_log (bed_id, patient_id, admission_id, assigned_at, status)
    VALUES (NEW.bed_id, NEW.patient_id, NEW.admission_id, NEW.admission_date, 'ACTIVE');
END

Timing, eventAFTER INSERT ON bed_assignment_log

Why a triggerLeft from the original project.
Without itNothing. It is dead code: it costs a trigger invocation on every bed assignment and should be dropped.

8.4 after_prescription_dispense§s8-4§

Timing, eventAFTER UPDATE ON prescription_items
What it doesWhen a prescription item changes from dispensed = FALSE to TRUE, subtracts its quantity from medicines.stock_quantity.
Why a triggerTies the stock total to the act of dispensing at the row level, in the same statement as the dispense UPDATE.
Without itWithout it, dispensed medicine would stay in stock_quantity and the total would no longer equal the sum of the batches (the dispense service takes the same quantity off the batches). If the trigger were removed, the service would have to decrement the total itself.
BEGIN
    IF OLD.dispensed = FALSE AND NEW.dispensed = TRUE THEN
        UPDATE medicines 
        SET stock_quantity = stock_quantity - NEW.quantity
        WHERE medicine_id = NEW.medicine_id;
    END IF;
END

8.5 audit_logs_no_delete§s8-5§

Timing, eventBEFORE DELETE ON audit_logs
What it doesRejects every DELETE on audit_logs.
Why a triggerAs above. Foreign-key cascades do not fire triggers, so the schema also avoids cascades into audit_logs. The FK to users is RESTRICT (users are deactivated, never deleted), and patient_id has no FK at all.
Without itAudit rows could be removed, for example to hide a read of a patient record.
BEGIN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'audit_logs is append-only: rows cannot be deleted';
END

8.6 audit_logs_no_update§s8-6§

Timing, eventBEFORE UPDATE ON audit_logs
What it doesRejects every UPDATE on audit_logs (SIGNAL 45000, "audit_logs is append-only: rows cannot be updated").
Why a triggerMakes the audit trail append-only for everyone, including the application. A bug, an attacker using the app's credentials, or a careless admin query cannot rewrite history. The app account has no TRIGGER, DROP or ALTER privilege, so it cannot remove the trigger either.
Without itAudit rows could be edited, which defeats the purpose of an audit trail.
BEGIN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'audit_logs is append-only: rows cannot be updated';
END

8.7 before_medicine_stock_update§s8-7§

Timing, eventBEFORE UPDATE ON medicines
What it doesRejects any UPDATE that would make medicines.stock_quantity negative (SIGNAL SQLSTATE 45000, "Medicine stock cannot be negative").
Why a triggerA last line of defence that holds for every writer. CHECK (stock_quantity >= 0) enforces the same rule (MySQL enforces CHECK since 8.0.16), so this trigger is a second guard with a clearer message.
Without itNothing on its own, because the CHECK remains. Remove both and an oversell would go through silently.
BEGIN
    IF NEW.stock_quantity < 0 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Error: Medicine stock cannot be negative.';
    END IF;
END

9.1 sp_admit_patient§s9-1§

Parameters: IN p_patient_id INT, IN p_doctor_id INT, IN p_bed_id INT, IN p_department_id INT, IN p_diagnosis TEXT

  1. INSERT one admissions row with admission_date = NOW() and status ACTIVE.
  2. The after_admission_insert trigger then occupies the bed, raises the workload and opens the bed log.

No checks of its own: an occupied bed or a doctor at their limit is not detected here, and CHECK doctors_chk_1 stops only the workload overflow. Not called by the API, whose admission code locks and checks first.

9.2 sp_allocate_emergency§s9-2§

Parameters: IN p_emergency_id INT

  1. Declare an EXIT HANDLER FOR SQLEXCEPTION that rolls back and signals "Emergency allocation failed".
  2. START TRANSACTION.
  3. Read the case FOR UPDATE, if it is WAITING or TRIAGED. If its patient_id is NULL, roll back with "not found or not waiting". (An arrival not yet registered is therefore refused.)
  4. Pick the lowest-id AVAILABLE bed of the required type (any type when none is required) FOR UPDATE SKIP LOCKED, so concurrent allocations skip beds another transaction is taking. None: roll back.
  5. Pick the AVAILABLE doctor of the required specialization with the lowest workload below the limit, FOR UPDATE SKIP LOCKED. None: roll back.
  6. INSERT the admission (department = the bed's ward's department; the triggers fire).
  7. UPDATE the case to ADMITTED with the doctor and bed, then COMMIT.

The API does not call it. services/emergencyAllocationService.js implements the same idea in application code with plain FOR UPDATE, a doctor fallback, and the creation or linking of an EMERGENCY visit, which this procedure cannot do.

9.3 sp_discharge_patient§s9-3§

Parameters: IN p_admission_id INT

  1. UPDATE the admission to DISCHARGED with discharge_date = NOW(), only if it is ACTIVE.
  2. The after_admission_discharge trigger frees the bed, lowers the workload and closes the bed log.

Does not cancel pending ward doses. The API discharge does (it cancels PENDING medication_administrations in the same transaction).

9.4 sp_generate_bill§s9-4§

Parameters: IN p_admission_id INT

  1. Read the admission's patient_id.
  2. INSERT a PENDING bill.
  3. INSERT one fixed line: "Base Consultation Fee", CONSULTATION, 1 × 500.00 (total_price is generated: quantity × unit_price).
  4. Set bills.total_amount to the SUM of its items.

No explicit transaction or locking, and a fixed fee: a demonstration procedure. Not called by the API.

9.5 sp_get_emergency_queue§s9-5§

A wrapper around the view. Not called by the API.

11. Transactions and concurrency§s11§

11.1 ACID as applied here

  • Atomicity. Every write path runs in one transaction (withTransaction: BEGIN … COMMIT, or ROLLBACK on any error). The audit row for a data change is written inside that transaction, so either the change and its audit row are both stored, or neither is; a test makes the audit insert fail and checks the change was rolled back. A dispense with one short item changes nothing at all: no stock, no batches, no items marked.
  • Consistency. Constraints (87 FKs, of which 15 composite consistency keys; 30 CHECKs, 23 unique keys, ENUMs, NOT NULL, strict SQL mode, a generated column), triggers (beds, workload, stock, audit) and the invariants the services keep (stock total = sum of batches, appointment status = visit status). Errors return a clear 4xx before anything is written.
  • Isolation. InnoDB at REPEATABLE READ (the server default; the app does not change it). Plain reads see a consistent snapshot. Every read that a later write depends on is a locking read (FOR UPDATE or FOR SHARE), so it sees the latest committed row and holds it until commit. Pessimistic locking, not version numbers, is the pattern throughout.
  • Durability. InnoDB's redo log; the binary log is on (log_bin = 1); migrate.js backs up before every migration; and the hosted demo takes nightly dumps, keeping 7 (restore tested).

11.2 Pessimistic locking and lock order

A deadlock needs two transactions waiting on each other's locks in a cycle. Every multi-row write path here locks rows in one fixed global order, so no cycle can form:

11.3 The dispensing deadlock (fixed)

Before. The original dispense locked the medicines rows through a join, in the order the items happened to be stored. Two prescriptions for the same pair of medicines in opposite order, [A, B] and [B, A], each locked one medicine and waited for the other. InnoDB detected the cycle and killed one with ER_LOCK_DEADLOCK (1213).

Fix. The fix has three parts:

  1. Total the quantity per medicine, which also merges two lines of the same medicine.
  2. Lock the medicines one row at a time in ascending medicine_id (server/utils/medicineLocks.js).
  3. Only then check stock and lock batches.

The same bug from another angle. Inserting a prescription_items row takes a shared lock on the referenced medicines row (the foreign-key check). A prescription created at the same moment as a dispense took those shared locks in item order, which could still cycle with the dispense's exclusive locks. Prescribing now takes FOR SHARE locks on its medicines up front, in the same ascending order.

Evidence. Tests with 30 concurrent rounds each (opposite item order; prescribing during dispensing; stock receipts during dispensing) and an opt-in stress test (300 rounds × 2 scenarios) record 0 deadlocks and stock that stays consistent.

11.4 The gap-lock issue (fixed)

Under REPEATABLE READ, a locking read through a secondary index takes next-key locks: the matching index records plus the gaps before them, which block inserts into those gaps.

Before. The dispense read its items with a locking read:

SELECT ... FROM prescription_items WHERE prescription_id = ? FOR UPDATE

That took next-key locks on the prescription_id index before taking the medicines locks. A concurrent prescription create already held medicines locks and then needed to insert items into that same index range, so it waited on the gap lock while the dispense waited on its medicines lock: a cycle.

Fix (server/services/dispenseService.js):

  • The items are read with a plain (non-locking) read. The prescriptions row lock already serialises every dispenser of that prescription, and nothing else modifies its items.
  • Items are marked dispensed with an UPDATE by primary key (WHERE item_id IN (…) AND dispensed = FALSE), which locks only those records, not gaps.

The emergency allocator has the same kind of fix. It finds the doctor's open visits with a plain read, then locks them by primary key in id order. A locking read through the (patient, status) index would lock the index entry before the row, while a concurrent "start visit" holds the row and then updates that index entry.

12. Integrity and security§s12§

12.1 Entity integrity

Every table has a primary key: an AUTO_INCREMENT integer surrogate, or version for schema_migrations. Primary key columns are NOT NULL by definition. Natural identifiers that must be unique carry unique keys:

  • username and email (users);
  • a department's name;
  • an ambulance's vehicle_number;
  • a bed code within its ward;
  • a batch number within its medicine;
  • an ABHA number (NULLs allowed);
  • a stored file name.

12.2 Referential integrity

87 foreign keys (72 relationships and 15 composite consistency keys, section 3); every ON UPDATE rule is NO ACTION (InnoDB treats it as RESTRICT). Primary keys are surrogates and are never updated, so cascading updates are not needed. ON DELETE rules:

  • RESTRICT (54) wherever the child has a life of its own, e.g. a patient with visits cannot be deleted.
  • CASCADE (12) where the child is part of the parent: bill_items of a bill, prescription_items of a prescription, the result of an order, attachments of a result, a doctor's schedules and analytics.
  • SET NULL (8) for optional references whose loss should not delete the child: an emergency's ambulance, assigned doctor and assigned bed; an admission's emergency case; a note's appointment; a lab order's note; a lab test's department; the technician on a result.

Some CASCADEs are questionable in a clinical system, and a few rules are inconsistent:

  • Deleting an admission would delete its bills (bills_ibfk_2) and its consultations (consultations_ibfk_4).
  • Deleting a patient or doctor would delete their surgery requests (surgery_requests_ibfk_1/2).
  • A consultation's prescriptions cascade (prescriptions_ibfk_1), while its lab orders are SET NULL.

In practice nothing deletes these rows: the API has no DELETE routes at all (records are cancelled or deactivated). The rules are still part of the schema, and listed in section 3.

12.3 Domain integrity

  • Types: DATE and TIME for clinical dates, DECIMAL for money and lab values, and small integers for vitals.
  • ENUMs for every status and code (e.g. appointments.status, beds.bed_type, prescription_items.route).
  • 29 CHECK constraints, for example:
    • impossible vitals (pulse 20–250, SpO2 50–100, temperature 25.0–45.0 °C, systolic above diastolic, both or neither BP value);
    • a vital reading filed under a visit or an admission;
    • dates in order (discharge after admission, an assignment's end after its start);
    • non-negative stock and money;
    • paid ≤ total;
    • an ABHA number of exactly 14 digits;
    • an ADMINISTERED dose has a time.
  • SQL mode includes STRICT_TRANS_TABLES, so an out-of-range value or a bad ENUM value is an error, not a silent truncation.
  • The API adds the rules a schema cannot express: a date of birth not in the future, a dose that includes a unit, and the visit-state machine.

12.4 Role-based access

  • Roles. Six roles live in users.role. A JWT carries the role, and every route declares the roles allowed (authorize(...)).
  • Which patients. server/utils/patientAccess.js decides patient by patient:
    • a doctor sees their care set (query 1: a UNION over appointments, admissions, consultations, lab orders, prescriptions and encounters);
    • a nurse sees active admissions in the wards assigned today, plus open outpatient visits;
    • front desk and admin see demographics but not clinical notes;
    • lab and pharmacy see their own work.
  • Audit. Denied requests are answered 403 and audited (outcome DENIED).

12.5 The restricted database user

The application connects as hospital_app, which has exactly these grants:

GRANT USAGE ON *.* TO hospital_app
GRANT SELECT, INSERT, UPDATE, DELETE, EXECUTE ON hospital_db.* TO hospital_app   (and the test/demo databases)
  • It cannot CREATE, ALTER or DROP anything, create or drop triggers, GRANT, LOCK TABLES, read or write files, or touch another database.
  • Triggers, views and procedures run with their definer's rights, so they keep working.
  • The server refuses to start as root.
  • Migrations, backups and the schema diff use a separate admin account (DB_ADMIN_USER), only for those tools.
  • On the hosted demo, the web server process does not even have the admin credentials in its environment.

12.6 The immutable audit log

  • audit_logs is append-only: BEFORE UPDATE and BEFORE DELETE triggers reject every change (section 8).
  • Data changes are audited in the same transaction as the change; reads and denials are written by middleware after the response.
  • details holds ids, enum values and changed field names only, never passwords, tokens or note text. A test plants a marker string in a note and checks it never reaches the log.
  • The foreign key to users is RESTRICT, and accounts are deactivated rather than deleted.
  • patient_id deliberately has no foreign key, so no patient change can cascade into the trail.

12.7 The migration system

  • Numbered files in database/migrations (000–014) are applied in order by server/scripts/migrate.js and recorded in schema_migrations.
  • 000 is a schema-only snapshot of the live database; on an existing database it is only marked as applied.
  • Before applying anything to a database that has tables, migrate.js takes a mysqldump backup.
  • Migrations are additive (new tables, nullable columns, guarded DDL), so they are safe to re-run.
  • Each one was rehearsed on a copy of live data first.
  • scripts/schema-diff.js compares hospital_db with the test database (tables, columns, indexes, FKs, checks, triggers, routines, views, events) and must report no differences.

14. Viva questions§s14§

Forty likely questions with short model answers, roughly in the order of this report. The last ones are about weaknesses and trade-offs.

  1. How many tables, views, triggers and procedures does the database have?

    33 tables (32 for the hospital, plus schema_migrations), 9 views, 7 triggers, 5 stored procedures, no stored functions and no events. There are 87 foreign keys (72 relationships plus 15 composite consistency keys), 30 CHECK constraints and 140 indexes (33 primary, 23 unique, 84 other).

  2. Why surrogate integer keys instead of natural keys?

    Natural identifiers are missing (most patients have no ABHA number), change (phone, name) or are composite. A small, immutable integer keeps foreign keys narrow and makes InnoDB's clustered index compact. Natural identifiers that must be unique get unique keys instead.

  3. What is the difference between appointments and encounters?

    An appointment is a booking (a slot). An encounter is the visit itself, with its own lifecycle and timestamps, and can exist without an appointment (walk-in, emergency, inpatient). An appointment has at most one encounter (unique appointment_id), and the appointment's status mirrors the visit's.

  4. Is the schema in 3NF?

    24 of the 33 tables are in BCNF. The other 9 are deliberately not in 3NF: eight copy a patient, doctor or medicine that is also reachable through an optional visit, admission, note or batch, and prescription_items keeps a dispensed flag next to its timestamp. Composite foreign keys make the database enforce the eight copies, and a CHECK constraint the dispensed flag. Section 6.4 lists each case and what keeps it consistent; section 6.3 lists the four decompositions made.

  5. Give an example of a partial dependency in this schema.

    There is none now; there were three. medication_administrations has the candidate key (prescription_item_id, scheduled_at_utc), and it stored patient_id, which depends on prescription_item_id alone: that failed 2NF. Migration 022 removed the column; the patient is read through the prescription. beds.floor (ward_id → floor) and appointments.department_id (doctor_id → department_id) were removed for the same reason.

  6. Why keep medicines.stock_quantity when batches already hold the stock?

    It makes "how much of X do we have" a single-row read and gives the CHECK and trigger one place to stop overselling. The cost is an update anomaly risk. That risk is controlled by changing both in one transaction under the same locks, by the dispense trigger, and by an invariant query that finds any mismatch (query 10).

  7. What would you change about medicines.expiry_date?

    Drop it, or turn it into a view column (MIN of the unexpired batch expiries). Since batches were added, it is not maintained and can mislead.

  8. How is a double booking prevented?

    UNIQUE (doctor_id, appointment_date, appointment_time). The second insert fails atomically with ER_DUP_ENTRY, and the API returns 409. Weakness: only identical start times collide, so overlapping appointments are not detected.

  9. How is double dispensing prevented?

    The dispense locks the prescriptions row FOR UPDATE, so a second dispense waits. When it resumes it sees status DISPENSED and returns 409. The item update also requires dispensed = FALSE and checks the affected-row count. A test sends two dispenses at once and exactly one succeeds.

  10. What causes a deadlock, and how did you remove the dispensing one?

    Two transactions each holding a lock the other needs. Dispenses locked medicines in item order, so [A,B] and [B,A] formed a cycle. Every path now locks medicines one by one in ascending medicine_id (FOR UPDATE to dispense, FOR SHARE to prescribe), so no cycle can form. Stress tests show 0 deadlocks over hundreds of rounds.

  11. What is a gap lock, and where did it bite?

    Under REPEATABLE READ, a locking read on a secondary index also locks the gaps between index records, blocking inserts there. The dispense's FOR UPDATE read of prescription_items by prescription_id locked that index range before the medicines rows, and a concurrent prescription create needed to insert there while holding medicines locks. The fix is a plain read (the prescription row lock already serialises dispensers) and an update by primary key.

  12. Why not use SERIALIZABLE isolation instead of explicit locks?

    SERIALIZABLE turns every plain SELECT into a shared locking read. That would make deadlocks more likely and slow every read. Explicit FOR UPDATE / FOR SHARE on the few rows a decision depends on gives the same safety where it matters, with a lock order we control.

  13. What does FOR UPDATE SKIP LOCKED do in sp_allocate_emergency?

    It skips rows locked by another transaction instead of waiting. Two concurrent allocations therefore take different beds and doctors immediately rather than queueing. The trade-off is that the "best" bed may be skipped. The API's allocator uses plain FOR UPDATE instead.

  14. Why are some rules triggers and others application code?

    Triggers hold for every client (API, stored procedures, admin SQL) and run in the same statement: bed occupancy, workload, stock decrement, audit immutability. Rules that need context the database does not have (the user's role, the patient's assignment, the visit state machine, the Five Rights at the bedside) live in the application.

  15. What is the weakness of the admission triggers?

    They act only on INSERT (occupy) and on the exact UPDATE ACTIVE → DISCHARGED (release). An admission inserted already DISCHARGED occupies a bed forever. The seed data did this, and migrations 004/005 repaired it. A TRANSFERRED status is not handled at all.

  16. Why is there a trigger that does nothing?

    after_bed_assignment_log has an empty body, left from the original project as a placeholder. It should be dropped.

  17. How is the audit log made tamper-resistant?

    BEFORE UPDATE and BEFORE DELETE triggers raise an error. The app account cannot drop triggers. Nothing cascades into the table, because the users FK is RESTRICT and patient_id has no FK. Data changes are audited in the same transaction, and details never hold secrets or note text.

  18. Can root still alter the audit log?

    Yes: an account with TRIGGER and DROP privileges (root, or the admin account used for migrations) can drop the triggers and then change rows. Database-level immutability protects against the application and its credentials, not against the DBA. For that you would copy the log to write-once storage or another system, and review the admin account's use.

  19. Why does audit_logs.patient_id have no foreign key?

    A foreign key would either block patient changes (RESTRICT) or cascade into the audit table, and cascades do not fire the immutability triggers. The audit trail must outlive any patient-record change, so it stores the id as a plain indexed value.

  20. What privileges does the application account have?

    SELECT, INSERT, UPDATE, DELETE and EXECUTE on its own database only: no DDL, TRIGGER, GRANT, FILE or LOCK TABLES. A SQL-injection or a stolen password cannot change the schema or remove the audit triggers.

  21. How are migrations made safe?

    Each is additive and guarded (IF NOT EXISTS, information_schema checks), so a failed run can be repeated. migrate.js backs up first and records versions in schema_migrations. Each migration is rehearsed on a copy of live data, and a schema diff against the test database must be empty.

  22. Which relationships are many-to-many and how are they implemented?

    Prescriptions and medicines (prescription_items); prescription lines and batches (prescription_item_batches); nurses and wards over time (nurse_ward_assignments). lab_orders is an associative entity between patients, doctors and lab_tests, and bed_assignment_log one between beds and admissions over time.

  23. Which relationships are one-to-one?

    lab_orders → lab_results (unique order_id) and appointments → encounters (unique appointment_id), both 1 to 0..1. users → doctors is 1 to 0..1 as well: doctors.user_id has been UNIQUE since migration 021.

  24. Why are some foreign keys ON DELETE CASCADE?

    Where the child cannot exist without the parent: bill_items, prescription_items, a lab result, attachments. Some CASCADEs are questionable for clinical data (deleting an admission would delete its bills and consultations). They are safe only because nothing deletes those rows.

  25. What is the redundant index in this schema?

    appointments has UNIQUE (doctor_id, appointment_date, appointment_time) and also idx_appointments_doc_date_time on the same columns. The second adds write cost and storage for no benefit.

  26. Why does idx_patients_name not help the patient search?

    The search uses name LIKE '%text%'. A leading wildcard cannot use a B-tree index, so MySQL scans. Options: a FULLTEXT index, a prefix search, or a separate search column.

  27. Explain idx_medicine_batches_fefo.

    (medicine_id, expiry_date, batch_id) matches "WHERE medicine_id = ? ORDER BY expiry_date, batch_id FOR UPDATE". The rows are found and locked in FEFO order without a sort, and every writer locks batches in that same index order, which prevents batch-lock deadlocks.

  28. Which views are updatable?

    MySQL reports available_beds_view, available_doctors_view, current_admissions_view, doctor_workload_view and pending_bills_view as updatable (one base table per UPDATE, no inserts through joins). The aggregate views and emergency_queue_view are not. The application writes only to base tables.

  29. Are the stored procedures used?

    Not by the API. They come from the original project. The API implements admission, allocation, discharge and billing in services with explicit locking, auditing and the visit lifecycle, which the procedures do not have.

  30. What does ACID atomicity mean concretely here?

    A dispense either marks every item dispensed, takes stock off the medicine total and batches, writes the batch trace, the ledger, the scheduled doses and the audit row, or does none of it. A test with one item short of stock checks that nothing changed.

  31. How do you keep appointment and visit status consistent under concurrency?

    One function performs every transition. It locks the appointment row then the encounter row, validates the transition against a fixed table, and writes both in the same transaction. Tests race a start against a cancel and check that exactly one wins and the mirror holds.

  32. How would you find data that violates an invariant?

    With GROUP BY … HAVING queries, e.g. query 10 (stock total ≠ sum of batches) and query 11 (patients with more than one active admission). An empty result means the invariant holds.

  33. What is the role of CHECK constraints vs ENUMs?

    ENUMs restrict a column to a fixed set (statuses, routes). CHECKs express ranges and cross-column rules (systolic > diastolic, paid ≤ total, end ≥ start). Both are enforced by MySQL 8.0.16+ for every writer. Before 8.0.16, CHECKs were parsed and ignored.

  34. Why store times in UTC in medication_administrations?

    Doses are scheduled and compared across days and shifts. Storing UTC (*_at_utc) avoids ambiguity from the server's time zone; the app converts to IST only for display.

  35. What is the cost of copying patient_id into many tables?

    Update anomaly risk (a row's patient could disagree with its visit's patient) and more storage. The benefit: direct filtering and access checks by patient without joining through optional parents. It is controlled by composite foreign keys (fk_ctx_*), which make the database refuse a copy that disagrees with its link, by resolving the parent for the given patient under a lock, and by never updating the copy.

  36. How would you prevent overlapping appointments, not only identical ones?

    Store a slot end time and check for overlap inside a transaction that locks the doctor's day, for example by locking the doctors row FOR UPDATE before checking. A plain unique key cannot express "no overlap" in MySQL.

  37. How is the "one active admission per patient" rule enforced?

    Not by the schema: MySQL has no partial unique index (UNIQUE WHERE status = 'ACTIVE'). The application checks it while holding the relevant row locks, and query 11 detects any violation. A generated column holding patient_id only when ACTIVE, with a unique index on it, would enforce it in the database.

  38. Is JSON in audit_logs.details a normalization problem?

    Strictly, it breaks 1NF, because a structured value sits in one column. It is accepted because details are never joined or filtered on. The indexed, queryable facts (user, action, entity, patient, outcome, time) are proper columns, and details holds only supplementary ids and field names.

  39. What are the biggest weaknesses of this database design?

    Stored totals and mirrors (stock, bill total, workload, bed status) that rely on triggers and application discipline; a redundant index; questionable CASCADEs; a stale medicines.expiry_date; free-text dose and frequency next to structured columns; triggers that miss some status paths; an empty trigger; unused original views and procedures.

  40. If you had one more migration, what would it contain?

    Drop idx_appointments_doc_date_time and the empty trigger. Change bills→admissions and consultations→admissions to RESTRICT. Add a generated-column unique key for one active admission per patient. Drop medicines.expiry_date, or replace it with a view column.
